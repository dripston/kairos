# Deploying the Kairos backend (and connecting the demo site)

The backend is one FastAPI app (`backend/kairos_backend/api.py`), pure Python standard library plus FastAPI,
uvicorn, httpx and tzdata. It needs **no database server** (SQLite files), **no keys** (models switch off
without one) and sends **nothing real** (every channel is a mock unless explicitly configured). It serves the
API, the live dashboard (`/demo/live`), the CM-03 console (`/cm03/console`), the two journey pages
(`/demo/journey/outbound`, `/demo/journey/inbound`, landing on `main` today) and API docs (`/docs`).

Checked: from a clean checkout of `main`, `uvicorn kairos_backend.api:app` with no key and mock channels answers
`/health`, `/demo/live`, `/cm03/console` and `/docs` with 200.

## Option A: Render (recommended, about 10 minutes, free)

1. Sign in at render.com with the GitHub account that can see `dripston/kairos`.
2. **New → Blueprint** → pick `dripston/kairos`. Render reads [`render.yaml`](render.yaml) and proposes one web
   service, `kairos-backend` (root `backend/`, build `pip install -r requirements.txt`, start
   `uvicorn kairos_backend.api:app --host 0.0.0.0 --port $PORT`, health check `/health`).
3. When it asks for **`SARVAM_API_KEY`**: paste the Sarvam key, or leave it empty to run without AI models.
   The three internal secrets are generated by Render. Channels are fixed to `mock`.
4. **Apply.** First build takes 2–4 minutes. Open `https://<service>.onrender.com/health`: you should see
   `{"ok":true,"policy_version":"1.1.1","env":"SIMULATED"}`.
5. Free services sleep after about 15 idle minutes and take about a minute to wake. **Open `/health` a couple of
   minutes before presenting.** The disk resets on restart, which is fine: all data is synthetic and re-seeded.

Without the blueprint (New → Web Service): same repo, Root Directory `backend`, Runtime Python 3, Build
`pip install -r requirements.txt`, Start `uvicorn kairos_backend.api:app --host 0.0.0.0 --port $PORT`, plus the
environment variables below.

## Option B: Railway / Fly / any VM

Same three facts everywhere: working directory `backend/`, install `pip install -r requirements.txt`, start
`uvicorn kairos_backend.api:app --host 0.0.0.0 --port $PORT` (Python 3.9+; 3.11 recommended).

## Option C: a laptop + a public tunnel (fallback for the demo)

```bash
cd backend && pip install -r requirements.txt && uvicorn kairos_backend.api:app --port 8000
```

Then expose it with a tunnel you trust (for example Cloudflare's `cloudflared tunnel --url http://localhost:8000`,
which you install yourself). The laptop must stay awake.

## Environment variables: what to put where

The full, commented list is [`backend/.env.example`](backend/.env.example). For a public demo you need at most:

| Variable | Value | Why |
|---|---|---|
| `SARVAM_API_KEY` | the Sarvam key (`sk_…`), or empty | turns on sarvam-prism, sarvam-105b-conversations and deepseek; everything works without it |
| `KAIROS_CHANNELS` | `mock` | nothing is ever sent from a public server |
| `KAIROS_CM03_DEMO_INBOX` | `1` | the CM-03 console shows the OTP it "sent" (synthetic numbers only) |
| `KAIROS_CM03_SECRET`, `KAIROS_REPORT_SALT`, `KAIROS_EMAIL_HASH_KEY` | long random strings | OTP signing and hashing; Render generates them |

Where the key goes:
- **On a host:** in the host's Environment settings (Render → service → Environment). Never in a file in the repo,
  an issue, a PR, a commit message or a chat.
- **On a laptop:** in `backend/.env` (git-ignored; `git check-ignore backend/.env` must print the path). Locally the
  backend reads only `SARVAM_API_KEY` from that file; every other setting is a normal environment variable.
- If a key was ever pasted somewhere shared (a chat, an issue, a screenshot), rotate it in the Sarvam dashboard
  after the event.

Leave every "real send" variable (`KAIROS_DEMO_*`, `WA_TOKEN`, `KAIROS_SMTP_*`) unset on any shared deployment.
The one exception is **CM-03 live WhatsApp** for a demo: `KAIROS_CM03_LIVE_WHATSAPP=1`, `WA_TOKEN`, `WA_PHONE_NUMBER_ID`,
`WA_APP_SECRET`, `WA_VERIFY_TOKEN` and a one-number `KAIROS_DEMO_ALLOWLIST`. The owner of that phone sets these
themselves, following [docs/LIVE_WHATSAPP.md](docs/LIVE_WHATSAPP.md). Unset them after the demo.

## Connecting the demo site (GitHub Pages) to the backend

The Pages build runs on built-in mock data while `KAIROS_PUBLIC_API` is unset.
1. GitHub → `dripston/kairos` → Settings → Secrets and variables → Actions → **Variables** → New repository variable:
   `KAIROS_PUBLIC_API` = `https://<service>.onrender.com` (no trailing slash).
2. Actions → "Deploy frontend to GitHub Pages" → **Run workflow** on `main`.
3. Or, without rebuilding: open `https://dripston.github.io/kairos/?api=https://<service>.onrender.com`
   (remembered in that browser; `?api=none` resets).

CORS is already open (`allow_origins=["*"]`), so the Pages site can call the backend directly.

## Revising the frontend: brief for whoever (or whichever Claude) does it

Feedback from the team lead after looking at https://dripston.github.io/kairos/: it is too complex and
overwhelming, there is no way to show the two journeys, and no way to show a human agent barging in. Target:

1. **Very simple, calm, cream.** Background cream `#FBF8F1`, white cards, 1 px `#E7E5E4` borders, ink `#1C1917`,
   one accent `#0F766E`; green = paid, amber = waiting for a person, red = STOP / blocked. System font, large type,
   generous whitespace, no glows or gradients. Light theme only for the demo.
2. **Four places, not twelve.** Navigation: **Home**, **Journey 1: Outbound collections**, **Journey 2: WhatsApp
   servicing**, **Take control** (approvals, holds, takeovers). Everything else (cohorts, campaigns, voice bots,
   learning, CRM, audit) goes under one **More** menu.
3. **Home** = one sentence on what Kairos does, four numbers (recovered, cost per ₹100, promises, rule breaches 0),
   two big cards that open the journeys, and a "Needs you" list of 1–3 approvals.
4. **Journeys.** The backend serves both as finished presenter pages: `/demo/journey/outbound` (real engines
   running, with pause, approve or reject, override, hold, STOP) and `/demo/journey/inbound` (borrower phone, live
   engine trace, **Take over** and **Hand back to bot**). With a backend configured, open them full-screen (link or
   iframe from the journey cards). Without one, show the journey's recorded walkthrough instead.
5. **Human barge-in must be visible** on Take control: queue of conversations and held decisions, each with a
   plain reason, and buttons **Take over / Approve / Reject / Hold**, every action echoed in a short audit list.
6. **Demo mode is not an error.** When `VITE_KAIROS_API=none`: no "API unreachable / offline" banners or pills
   anywhere, one quiet "Demo data · SIMULATED" tag in the top bar. Real errors only when an API is configured and
   fails.
7. **Plain words.** No raw rule ids (`APPROVAL_REQUIRED` → "Waiting for a supervisor"; the id in a tooltip), no
   decimals like "0.322 replies per ₹" (→ "32 replies per ₹100"), masked names only.
8. **Done when:** every nav item renders cleanly in demo mode at 1440×900 and 1920×1080 with no horizontal
   scroll, `npm run lint` and `npm run build` pass, and CI is green.
